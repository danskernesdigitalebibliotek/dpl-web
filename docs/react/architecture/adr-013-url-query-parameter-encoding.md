# ADR 013: Encode URL query parameters exactly once via URLSearchParams

## Context

The apps use URL query parameters to carry state across page loads and
redirects: the `modal` parameter reopens modals (its id can embed a Pid
containing a colon, e.g. `870971-tsart:34310815`), the search `q` parameter
carries free text, and `advancedSearchQuery` carries JSON. During the login
flow a parameter travels **two** hops: it is first written into the return
URL's query, and that whole path is then carried as the `current-path`
parameter on the auth URL. The CMS decodes `current-path` once and redirects
back to it.

The URL helpers historically layered `encodeURI()` on top of
`URLSearchParams.set()` when writing, and `decodeURI()` on top of
`URLSearchParams.get()` when reading. `URLSearchParams` already
percent-encodes and decodes symmetrically on its own. `encodeURI` does not
touch reserved characters such as `:`, but it does escape `%` (to `%25`), so
every extra hop added an encoding layer. `decodeURI` cannot compensate: per
spec it does not decode reserved characters (`%3A` stays `%3A`).

Concretely, the digital copy modal id went `:` → `%3A` → `%253A` across the
two hops but was only decoded once on return, so it no longer matched the
mounted modal: the modal did not reopen after login and the body scroll
stayed locked. The same asymmetry corrupted reserved characters in `q` and
could crash `advancedSearchQuery` JSON parsing (`decodeURI` throws on a
literal `%` sequence).

## Decision

`URLSearchParams` is the single encoding and decoding authority for query
parameters:

- Writers pass raw values to `URLSearchParams.set()`/`append()`.
- Readers return `URLSearchParams.get()`/`getAll()` output untouched.
- Never layer `encodeURI`/`encodeURIComponent`/`decodeURI` on top of values
  that pass through `URLSearchParams`.

With every hop encoding and decoding exactly once, values round-trip
correctly through any number of hops — including the login redirect.

For readability, `prettifyQueryColons()` rewrites `%3A` back to `:` in the
serialised query at the points where we write to the address bar (history
push/replace), so deep links read `?modal=digital-modal-870971-tsart:34310815`.
A colon is a legal query character (RFC 3986 §3.4) and `URLSearchParams`
parses `:` and `%3A` identically. The rewrite cannot corrupt data: a
*literal* `%3A` in a value serialises as `%253A` and is not matched.

Unit tests in `src/tests/unit/url.test.ts` pin the single-encode round-trip,
the login-redirect double hop, and the pretty-colon behaviour.

## Alternatives considered

### Sanitise reserved characters out of the modal id

An initial workaround replaced the colon in `createDigitalModalId` with a
URL-safe character. It fixed only that one parameter, left the underlying
asymmetry in place for every other parameter, and made the id diverge from
the raw Pid. Reverted in favour of this decision.

### Keep double-encoding and decode twice on read

This would perpetuate the extra layer and break every reader that is not our
helper: the Modal component reads with plain `URLSearchParams` (one decode),
and the CMS decodes `current-path` once. External consumers cannot be
expected to double-decode.

### Hand-roll query serialisation that leaves colons unencoded

Reimplements platform behaviour and is easy to get wrong for the characters
that *do* need encoding. The display-only rewrite achieves the same
readability without owning serialisation.

## Consequences

- Query parameters round-trip losslessly; new parameters need no special
  encoding handling as long as they go through the URL helpers.
- Links generated by the previous double-encoding code (old bookmarks and
  shared links, e.g. `q=harry%2520potter`) are read back with one residual
  layer after this change ("harry%20potter"). This is self-healing — all
  newly written URLs are correct — and unavoidable without reintroducing the
  asymmetry.
- Re-adding `encodeURI`/`decodeURI` around `URLSearchParams` would reintroduce
  the bug; the unit tests guard against this.
